## Background: what "stateless" refers to

The MCP TypeScript SDK has a `2.0.0-beta` line in progress
(`modelcontextprotocol/typescript-sdk`, tags `@modelcontextprotocol/server@2.0.0-beta.1..5`)
implementing the **2026-07-28** protocol revision. Two separate things are called
"stateless" and it's worth not conflating them:

1. **Transport-level stateless mode** (already available in 1.x, not new): setting
   `sessionIdGenerator: undefined` on `StreamableHTTPServerTransport` makes it create
   one transport per HTTP request instead of pinning a client to a long-lived
   session via `Mcp-Session-Id`. This is an **HTTP-transport-only** concept.
2. **Package/architecture rewrite in 2.0**: the SDK is splitting from a single
   `@modelcontextprotocol/sdk` package into:
   - `@modelcontextprotocol/core` — shared schemas, OAuth, protocol constants
   - `@modelcontextprotocol/client`, `@modelcontextprotocol/server` (versioned together)
   - Framework adapters: `@modelcontextprotocol/node`, `@modelcontextprotocol/hono`,
     `@modelcontextprotocol/fastify`, `@modelcontextprotocol/express`

   The 2026-07-28 spec revision itself also carries breaking wire changes:
   `serverInfo` moves from the result body to `result._meta`, `clientInfo` goes from
   required to SHOULD, tool-result caching changes representation
   (JSON-serialized documents instead of live object graphs — drops the
   `structuredClone` dependency), CJS builds ship alongside ESM with normalized
   extensions (`.mjs`/`.d.mts`, `.cjs`/`.d.cts`).

## Relevance to szkrabok

szkrabok is **stdio-only** — `docs/mcp-client-library.md` explicitly lists "HTTP
transport" under "What is NOT in scope." Item (1) above (stateless
`StreamableHTTPServerTransport`) therefore doesn't apply to us directly: we never
construct that transport, in `src/server.js` or the test client
(`packages/runtime/mcp-client/runtime/transport.js`, which uses
`StdioClientTransport`/`StdioServerTransport` only).

Item (2) — the 2.0 package split and wire protocol revision — is what would
actually affect us, because:

- `src/server.js` imports from `@modelcontextprotocol/sdk/server/index.js`,
  `/server/stdio.js`, `/types.js`.
- `packages/runtime/mcp-client/runtime/transport.js` imports from
  `@modelcontextprotocol/sdk/client/index.js`, `/client/stdio.js`.
- Neither subpath is guaranteed to exist unchanged under
  `@modelcontextprotocol/server` / `@modelcontextprotocol/node` — the beta docs
  describe stdio living under a `node`-specific adapter package in the new layout,
  not bundled into a generic `server` package the way 1.x bundles `server/stdio.js`.
- `server.oninitialized`, `server.listRoots()`, `setRequestHandler` usage in
  `src/server.js` needs re-verification against the 2.0 `Server`/`McpServer` API —
  the beta notes mention `McpServer` as the primary construct in examples, not the
  lower-level `Server` class we currently use.
- `packages/runtime/mcp-client/codegen/generate-mcp-tools.mjs` bakes a
  `REGISTRY_HASH` from `client.listTools()` — needs confirming `listTools()` shape
  is unchanged (result body vs. `_meta` move could affect other calls, not
  `listTools` itself, but worth checking against the spec diff).

## Recommendation

Do not track `2.0.0-beta` yet. Reasons:

- It's beta (5 pre-releases as of this writing, no stable tag) — conflicts with
  this repo's "deliberate upgrades, tested before they land" dependency policy
  (`docs/development.md` § Dependency pinning).
- It's a multi-package migration (`sdk` → `core`+`server`+`node`), not a version
  bump — `npm run deps:update` / exact-pin bump workflow doesn't cover swapping
  package names. This needs a dedicated migration, not a routine dependency PR.
  Also touches `packages/runtime/package.json` (used by both the MCP server and
  the test client) and the codegen script's import of `Client`.
  affects the wire format tests assert against (`tests/node/contracts.test.js`,
  `tests/node/schema.test.js` — names inferred from `test:contracts` output above,
  verify exact files before starting).

## If/when this is picked up later

1. Wait for a stable `2.0.0` tag (or re-evaluate if a beta becomes unavoidable,
   e.g. security fix only shipped on 2.0).
2. Read the SDK's own migration guide (referenced in the 2.0 release notes as
   "migration guides for upgrading from v1" — locate under
   `modelcontextprotocol/typescript-sdk` docs at that time, path unknown as of
   this writing since only beta tags exist).
3. Identify the correct stdio-serving package for the new layout (likely
   `@modelcontextprotocol/node`, per the `NodeStreamableHTTPServerTransport`
   naming pattern seen in Context7 docs — confirm whether an equivalent
   `NodeStdioServerTransport` or similar exists, or whether stdio stays in
   `@modelcontextprotocol/server`).
4. Re-verify `server.oninitialized` / `listRoots()` / `setRequestHandler` against
   whatever `Server` or `McpServer` API 2.0 ships — `src/server.js` is the only
   file using the low-level `Server` class.
5. Re-verify `Client` / `StdioClientTransport` equivalents used by
   `packages/runtime/mcp-client/runtime/transport.js` and the codegen script.
6. Run full `npm run test:self` + `npm run test:playwright` + `test:contracts`,
   regenerate `mcp-tools.js` (registry hash will change regardless — new SDK,
   possibly new schema shape) — expect this to be a multi-day, multi-commit
   migration, not a one-line bump like the 1.29→1.30 change in this document.
